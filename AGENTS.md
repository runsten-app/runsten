# AGENTS.md

Guide for contributors (human or AI) picking up work on Runsten. Read it before changing code.

## Project

Runsten is an open source data logger for Volvo and Polestar EVs, in the spirit of TeslaMate: it polls the vehicle APIs, stores the raw responses, reconstructs trips and charging sessions, and serves them through an API and a web UI.

- Language: Go (version pinned in `go.mod`), module `runsten`.
- Storage: PostgreSQL (pgx v5, `pgxpool`).
- Front end: Vue 3, TypeScript (strict), Vite, Vuetify, in `web/`; Node version pinned in `web/.nvmrc`. Served by the Go binary `runsten-web`.
- Multi-tenant: one account = one driver. Every row belongs to an account, isolated by row-level security.
- Licence: AGPL-3.0-or-later. Runsten is open core: a downstream build may add modules of its own through the extension points (see "Architecture rules"), never imported by public code. What only a hosted service needs (sign-in through an identity provider and sign-up, billing) does not belong here: the core targets self-hosting, down to a Raspberry Pi, with local passwords.

## Architecture rules

Enforced by `golangci-lint` (`.golangci.yml`); `task lint` must report 0 issues. Add a depguard rule whenever you introduce a package with a dependency constraint.

The import graph is also checked by `internal/archtest` (`TestDependencies`, after the standard library's `go/build/deps_test.go`): an exhaustive allowlist of the module's packages, third-party modules and adapter packages (`net/http`, `encoding/json`, `database/sql`) each package may import. A package missing from it fails the test. depguard gives the editor feedback and the reason; the allowlist catches what no deny rule foresaw. A new package or dependency updates both.

- **Dependencies point inward.**
  - `core` imports no adapter: no `net/http`, `database/sql`, pgx, `encoding/json`, `volvo`, `platform` or simulator.
  - `collector` knows neither HTTP, pgx, `store`, `derive`, `publish`, `polestar` nor `tesla`: it declares the interfaces it needs. It reads the Volvo API itself (`volvo`'s errors drive its reactions); another provider is a `Source` (`AddSource`), which `collector/polestarsource` and `collector/teslasource` adapt the Polestar and Tesla clients to, and whose errors they classify (`SourceError`).
  - `publish` knows neither the network nor the database: it builds the messages from `core` (and the discovery's JSON). The catalog stays out of it: `runsten-collector` implements its adapter's `Models`. `publish/mqtt` is the only package that imports paho (`github.com/eclipse/paho.mqtt.golang`); the embedded broker of its tests (`github.com/mochi-mqtt/server/v2`) never ships.
  - `derive` knows neither HTTP, pgx, `store`, `collector` nor `catalog`: it declares `Capacities`, which `runsten-collector` implements from the catalog.
  - `oauth` knows neither HTTP, pgx, `store`, `volvo` nor `collector`: the Volvo client implements its `Refresher`, the store its `Store`, and its `Manager` satisfies the collector's `TokenSource`.
  - `auth` knows neither HTTP, pgx, `store`, `api`, `volvo`, `oauth` nor `collector`: the store implements its `Store`, `api` turns its sessions into cookies.
  - `api` knows neither pgx, `store`, `volvo`, `collector` nor `derive`: the binary wires them.
  - `catalog` imports no package of the module. `api` imports it, as pure data like `core`, to recognize the variants on each read; `core` and `volvo` do not: recognizing is a reading, not a normalization. `runsten-api` and `runsten-collector` load it once at startup. The variant in effect is `catalog.Effective`: the user's choice while it holds (`catalog.Chosen`), else the recognized one (`catalog.Recognize`), the same for the reads and for the net capacities of the derivation. A source that tells the brand but not the family (the Polestar Data Portal: `core.Snapshot.Brand`) is matched among the brand's variants (`MatchBrand`), and the variant chosen sets its family. A new choice deletes the vehicle's derivation cursor (`store.SetVehicleModel`), so that the collector derives it again.
  - `volvo` depends on neither `store` nor `collector`.
  - `importer` knows neither HTTP, JSON, pgx, `store` nor `api`: it converts the values of `aximote` (the client, which knows no business code and returns Aximote's values as they are) and declares its `Store` and `Source`; the store implements the first, `aximote.Client` the second. `api` declares `ImportJobs` and `AximoteVehicles`, which `runsten-api` wires.
  - `platform` depends on no business code.
  - `flags` is pure data, as `catalog`: `api` reads its declarations and declares `Flags`, which `flags/eval`'s `Evaluator` implements; only the binaries import `flags/eval`, and only it imports OpenFeature (`github.com/open-feature/go-sdk`). See "Feature flags" below.
  - `release` is a client: `api` declares `Releases`, which `runsten-api` adapts the checker to. The binaries know their version from the build (`main.version`, `-ldflags -X`: the Dockerfile's `VERSION`, which `scripts/release-images.sh` passes), `dev` otherwise.
  - `web` knows neither pgx, `store`, `api`, `auth`, `core`, `volvo` nor `collector`: it reaches `runsten-api` over HTTP only, and holds no session, database or secret.
  - The simulator is used only by its binary and by tests.
  - Vendor-specific formats (Volvo JSON, the Polestar Data Portal's) are converted on the vendor side, never in `core`: both produce the same types.
- **Small interfaces, declared by the consumer.** Constructor injection, no mutable globals, no `init()` with side effects.
- **Injected time.** `time.Now` is forbidden outside `internal/platform` (forbidigo): take a `clock.Clock`. Tests use `clock.Manual`; the simulator uses `clock.Accelerated`.
- **No `fmt.Print*`**: log with `log/slog` (JSON handler in binaries). Log durations and enums with `.String()`.
- **Context and errors.** `context.Context` on every I/O. Wrap errors with `%w` (wrapcheck). Go style: lowercase, `"doing x: %w"`.
- **Extension points** for a downstream build that adds modules (the `premium` build tag), and only for a feature of it that exists: a binary's `extensions.go` (`//go:build !premium`) holds a function that does nothing, called explicitly by `main` with what the feature consumes; the downstream build adds its twin, a `cmd/**/premium*.go` file under `//go:build premium` (the only files depguard lets import `runsten/premium`), and runs everything with `GOFLAGS=-tags=premium`. A test that needs the public build's extensions is tagged `!premium` too (`cmd/runsten-api/extensions_test.go`), and `internal/archtest/extensions_test.go` declares the premium packages' allowlist, empty here, which the premium build's twin fills. No `init()`, no registry, no name of a private module. Today: `runsten-api`'s `registerExtensions` (its `ServeMux`, `getenv`, the database URL, the token key, `*auth.Service`, `*api.Server`, the flags' `*eval.Evaluator`, the HTTP client, the logger), which an extension uses to sign in a user authenticated otherwise (`auth.Service.Open`, a session, and `api.Server.SessionCookie`) and to read the JSON API as a user it authenticated (`auth.Service.AuthenticateToken`, the personal access tokens, and `api.Server.ServeAs`); the extension sets the `api.Server`'s `Limits` (what an account reads, and whether it has the costs, the statistics by interval, the CSV files and MQTT), `Admission` (a route of the web interface an account must go to before `/auth/volvo/start`, such as terms to accept, where it is sent; `PUT /connection/api-key` and `PUT /connection/polestar` refuse its account meanwhile, `403 not_admitted`, nothing stored), `MaxVehicles` (a Volvo ID or an application key giving access to more vehicles is refused, nothing recorded) and `ExportTables` (its own schema's tables, added to the account's export). `runsten-collector`'s (`getenv`, the database URL, `*collector.Collector`, the flags' `*eval.Evaluator`, the logger) sets the collector's read policy. In both, the extension may give the flags a provider of its own, with the instance's name (`eval.Evaluator.Use`), in place of `RUNSTEN_FLAGS`'s. The front end's are `src/app/extensions.ts`: `beforeStart` (awaited by `main` before the router's first navigation and the app's mount, to prepare the page first, such as replacing `globalThis.fetch`, which every API call looks up at each call); `src/app/routes/extensions.ts`: `extensionRoutes` (pages, which the other front end extensions link to; the core names only `signedOut`, where the sign-out ends instead of the sign-in page) and `extensionGuards` (run in order after the session guard; one may send to another page first). And `src/widgets/app-shell/extensions.ts`: `extensionNotices` (components shown in order at the top of every page of the shell, such as a payment to settle) and `extensionMenuItems` (entries of the user menu, after the settings and the connection, each in a `role="listitem"` the shell gives it); `src/pages/settings/extensions.ts`: `extensionSections` (components shown in order in the settings' integrations, after the access tokens and MQTT, each a section with its heading, an `h3`), `extensionAccountSections` (the same in the account's area, before its data) and `extensionAccountActions` (buttons after the download of the account's data); `src/pages/stats/extensions.ts`: `costsUnavailable` (a component the statistics' costs view shows instead of its message where the account's limits leave out the costs); `src/entities/session/extensions.ts`: `limitsPage` (where the account's limits are lifted, which every limit then leads to: the history's, a function or a vehicle left out, too many vehicles). The core words none of what these add. The `Dockerfile` copies `premium/` when the context has one and builds with `--build-arg TAGS` (empty: the public build). A change of these breaks the downstream build when it takes the new core, not this repository's: keep them few and small.
- **Feature flags** (ADR 0039): a function shipped off or on, which an instance, or an account, turns over without a new image; made to go, removed with its dead code at the latest by the release after the one that ships it on everywhere.
  - Declared once in `flags.All`: a name of dot-separated kebab-case words, the area first (`source.tesla`), its default, `Web` when the front end reads it, its purpose and when to remove it (`TestDeclarations`). Today: `source.tesla` (on; ADR 0040 §10), wired to nothing yet: the Tesla source will read it.
  - Evaluated by `eval.Evaluator` on an OpenFeature API of its own (`isolated.NewAPI`, never the SDK's global one). The context is the account's ID (`targetingKey`) and the instance (`instance`, given with the provider; none for `Env`), nothing else: no e-mail, no VIN. `Use` waits up to `eval.ReadyWait` for the provider: one ready by then gives its values from the first request; one not ready yet gives the defaults until it is, whatever it is configured with. A provider absent, not ready, in error, or slower than `eval.Timeout` (at best: the SDK does not enforce it, only a provider that honors its context stops) gives the default, as shipped; an initialization that fails, and each change of a flag's failure, is logged. The binaries stop it within 5 s.
  - The provider is the deployment's: `RUNSTEN_FLAGS` (`name=true|false`, by commas, the same for every account; an undeclared name is warned about and ignored, a value other than `true` or `false`, in any case, fails the configuration) through `eval.Env`, the SDK's in-memory provider; a downstream build's in its place through the binaries' extensions (`flags`, `Evaluator.Use`). Tests use `Env` or a provider of their own, without network.
  - The front end evaluates nothing: `GET /session` gives `flags`, the `Web` ones evaluated for the session's account (`api.Server.flagsOf`; its schema built from the declarations), read by `useFlag(name)` (`features/view-flags`), off until the session is known.
  - Not a flag: an account's offer (`limits.unavailable`), a lasting setting of the instance (a variable of its own), what a build adds (its extensions).
- **No speculative abstractions.** No event sourcing, no message bus: raw snapshots, derived tables that can be recomputed. A new dependency needs a justification in the commit message.

## Data model and security

- **Snapshots** are the source of truth: raw JSON per `(vehicle_id, source, endpoint, fetched_at)`.
  - `source` names where the readings come from (ADR 0035): `volvo` or `polestar` for the collector, by the vehicle's provider; each writer names its own, there is no default. `endpoint` is the source's own (a Polestar domain: `battery`, `availability`…).
  - Deduplication, within a source and an endpoint: SHA-256 of the canonical JSON without `timestamp`, `updatedAt` and `operationId`.
  - An identical response only advances `checked_at`. A value is therefore valid from `fetched_at` up to `checked_at`.
- **Derived data** (trips, charges) must be rebuildable from snapshots at any time, idempotently.
  - A record is two readings: its values at `fetched_at` and again at `checked_at`. Nothing is known in between (failed calls do not break a run of identical responses).
  - Times are bounds (`started_after`/`started_before`, `ended_after`/`ended_before`). Reconstructed events (never seen, revealed by the odometer or the SoC) lie in `[started_after, ended_before]`.
  - Incremental derivation resumes from `derivation_cursors`: events with `detected_at` after `settled_at` are replaced. Detection trackers must depend on the readings only, never on the state machines, or incremental and rebuild diverge (`TestIncrementalMatchesRebuild`, `checkRebuild`).
  - Ambiguous vendor behavior is isolated in `core.Params`.
  - A change to the derivation lists, before its code, the cases it must hold in, each a test: readings fetched at the same time (`points` orders them by field); one reading that tells several fields (a position with the odometer or the engine); a value read after another but recorded before it (vehicle timestamps out of order); each `core.Params` that changes it, such as `VehicleTimestamps` off; an incremental derivation against a rebuild (`TestIncrementalMatchesRebuild`). Check that each test fails without the change.
  - An event's `sources` are those of the readings from its `start.before` to its `end.before` (`core.Derive`, sorted): readings an incremental derivation replays as a rebuild does, never those before it.
  - A value an event takes from the latest readings (its capacity) is taken at the reading that ends it, never when the event is built: an event is built at the first reading after its settle window, which may be a confirmation an incremental derivation saw earlier than a rebuild.
  - A charge ended by done or idle with the cable connected may resume (`core.Params.MaxChargePause`, 24 hours): the vehicle seen charging again within it, before the cable is read disconnected, a trip starts or is revealed, or a reconstructed charge opens, goes on with the same charge (a solar charge stops and starts with the sun), and the charge as first reported is withdrawn. The cursor never settles while a charge may resume, so that a derivation that resumes it also detected it.
  - A plug-in hybrid (`core.Snapshot.Powertrain`, read from the details: Volvo's `fuelType` listing `ELECTRIC` among its fuels) has its engine raise the SoC while driving (a charge mode, charge sustain): a rise of `MinChargeSoC` or more read parked is a reconstructed charge only when the reading that shows it says the cable connected (`detector.onPlug`). The odometer would tell whether it drove, but parked it is read once an hour. A vehicle whose powertrain is not read yet keeps the rule of the SoC alone. `TestRealPlugInHybrids` derives two real V60s' responses, kept out of the repository, from the directory `RUNSTEN_V60_FIXTURES` names (skipped without it); `scenarios/v60-phev.yaml` stands in for them.
  - A charge's cost bills its `energy_soc_kwh`, or its `energy_power_kwh` when the SoC rose by less than `core.CostParams.MinSoCRise` (the derivation's `MinChargeSoC`): a small charge barely moves a SoC read in whole points.
  - A charge's position is the first one read after its end within the settle window, before a trip or another charge starts (the vehicle may upload it late, after the charge's end: unplugged at one charger and driven straight to another, unseen); else the one it had at its end.
  - A trip revealed by the odometer leaves a charge waiting for its position when it ended before that charge (the odometer's vehicle timestamp): it was the drive to it. When it may have ended after, the charge waits only for a position the vehicle recorded before the charge ended: some vehicles stamp the odometer when they upload it, not when the drive ends. It starts at the position the vehicle recorded before the odometer reading that last saw it parked, even one read after it (the readings a transition triggers come in order, the odometer before the position).
  - Energies are ΔSoC × a capacity chosen by `core.Params.Capacity`: `catalog_net` (default; assumption: the SoC runs over the net capacity) takes the net capacity of the effective variant, injected as a `core.NetCapacity`, else the reported `batteryCapacityKWH` (`api`). Each event stores the one it rests on (`capacity_kwh`, `capacity_source`). A new default, or a corrected net capacity in the catalog, changes past energies only through a rebuild: say so in the update notes (`documentation/self-hosting/updating.md`).
- **The charge in progress** (`GET /vehicles/{id}/charging`, `core.Result.InProgress`): the charge still open at the latest reading, never an event. The API replays the derivation from the vehicle's cursor (`derive.Deriver.InProgress`, nothing saved, the net capacity of `catalog.Effective` given by the API), so it has the start, the energies so far and the `DetectedAt` of the derived charge it becomes: its end is its latest reading (`End.After` the latest charging, `End.Before` the latest energy reading, later while paused). Priced by its place's tariff up to that reading, never an entered cost; the lists, their cursors and the statistics never count it. A finished charge is saved at the next pass, before its settle window: only the open one needed this. The front end shows it first in the charges list while the period reaches it, and links to it from the vehicle's charging tile (asked only while the cable is connected or the car charges), its page being the future charge's (`/charges/:id`, which shows the derived charge once over), and says the readings stopped past `collectorStoppedAfter` (15 minutes), never a charge that goes on.
- **Software versions** (migration `0028`): `core.FieldSoftware` covers `Snapshot.Software` (Tesla's `car_version` without its build hash, covered only when there is one, so that the latest response of the kind always tells the version a replay starts from) and `SoftwareUpdate` (`software_update`, absent when its status is empty; a status not known is `unknown`, an update all the same). The derivation reports each version read for the first time (`Result.Versions`, `core.SoftwareVersion`: installed after the last reading of the previous one, none for the first), stored in `software_versions` and replaced past the cursor as the trips. `InstallStarted` (migration `0029`) bounds its installation's start: after the last reading of the software without status `installing`, before the first one with it; an installation given up (another status, the same version) is forgotten, and none is told without a reading before it. The cursor never settles during an installation: a replay from after its start would lose it. The installation ended within `Installed`, the car telling the previous version until it restarts. `SoftwareUpdate.ScheduledAt` is Tesla's `scheduled_time_ms`. `GET /vehicles/{id}/state` gives `software` and `software_update`; `GET /vehicles/{id}/software-versions` the history, paged as the trips (`from`/`to`: may have been installed within).
- **Temperatures** (migration `0030`): `core.FieldClimate` covers `OutsideTempC`, `CabinTempC` and `Climate` (on, preconditioning, battery heater), Tesla's `climate_state` (°C, an assumption whatever the car displays); Volvo removed its external temperature from the Connected Vehicle API v2, the Polestar Data Portal tells none. `GET …/state` gives `climate`, each value a reading, null for a source without. A trip's `OutsideTempC` (`trips.outside_temp_c`) is the mean of the responses fetched from its `DetectedAt` to its `End.Before`, each once at its fetch, never at its confirmation (which moves as a run grows: an incremental derivation and a rebuild would differ), else the latest fetched before it (`detector.outside`, a tracker of the readings); none for a reconstructed or imported trip.
- **A Tesla's rated capacity** (migration `0027`): a charge keeps the range read with its start and end SoC and the usable level read with its end (`StartRangeKm`, `EndRangeKm`, `EndUsableSoC`; `core.FieldSoC` covers the usable level, Tesla's `usable_battery_level`, with the SoC). The battery page (`core.CapacityTrend`) reads the rated efficiency (median over the observed charges of `RatedMinDuration` or more ending at `MaxSpanSoC` at most of `energy_measured_kwh / Δrange`) and, per charge ending at `RatedMinSoC` usable or more, a `rated` estimate: `end_range / end_usable × 100 × efficiency`, as TeslaMate. Once `MinEstimates` of them, the current capacity, its change and the months rest on them alone (`Trend.Rated`, the API's `basis`); the other estimates stay in the series. Read on each request: a parameter needs no rebuild, the columns do.
- **Imported events** (migration `0019`, ADR 0030): trips and charges another application cut from its own readings (Aximote, the Volvo Cars app), never readings (those go into `snapshots` under their source).
  - `imported_trips`, `imported_charges`, and `imported_tracks` (a trip's GeoJSON LineString, deleted with it, read on demand by `GET …/trips/{id}/track` and drawn on the trip's map). Not derived: a rebuild never touches them. Each row names its `source`, in the vocabulary of `snapshots.source`, and its `source_id` there (URL-unreserved characters), unique per vehicle: a new import of the same event replaces the row, keeping its `id` and its track.
  - Written by `store.SaveImport` only, never by the API (a token reads): it takes what starts before the vehicle's first snapshot, of any source (the time of the import without one), and counts the rest as skipped, so that no import overlaps a derived event. An importer validates first: a row the checks refuse fails the whole import.
  - Read with the derived events, in one relation per kind (`tripEvents`, `chargeEvents` in `store/events.go`): their bounds are their exact times, `after` equal to `before`; their `detected_at` the time of their import; `import_key` (`source:source_id`, empty for a derived event) orders those that start at the same time and identifies them (`api.EventRef`). The lists, the details, the statistics and the CSV files take both; the battery's estimates take the derived charges only (an import has no power span).
  - A charge's energy from the application is its `energy_power_kwh` (a measured flow), its `energy_soc_kwh` the importer's ΔSoC × capacity, stated as the derivation's. Its cost is the application's (`core.Charge.PaidCost`, `cost.source` `imported`) when in the account's currency, else its place's tariff's; it takes no entered cost (`409 imported_charge`, `core.AttachCosts` skips it).
  - The account's export holds the three tables; `DELETE /vehicles/{id}/imports/{source}` deletes one source's events of a vehicle (the vehicle's settings).
  - The Volvo Data Portal's files are a Volvo's history: a Polestar refuses them (`409 not_volvo`), and its settings do not offer them.
- **Import jobs** (migration `0020`, ADR 0036): an import of a vehicle's history, asked for by `POST /vehicles/{id}/import-job` (session only, `202`) and run by `runsten-api`'s import worker (`internal/importer`), as the geocoding's.
  - `import_jobs`: the vehicle, the source and its vehicle there, the status (`pending`, `running`, `done`, `failed`), the step (trips, then charges) and the source's cursor, the counts (imported, skipped after the cutoff, invalid), the cutoff, the failure as a kind (`token_refused`, `source_failed`, `internal`). One active job per vehicle (`import_jobs_active`, `409 import_active`).
  - Claimed across the accounts by `runsten_claim_import(at, lease)` (`FOR UPDATE SKIP LOCKED`), which gives the account, the job and its claim only; the worker reads the job within the account. Each page writes its events (`SaveImport`'s rules) and the job's progress in one transaction, and renews the claim: a restart resumes at the cursor, a page is never counted twice, and a write of a claim another worker has taken over is refused (`claimed_at` compared).
  - A 429 puts the job back until `Retry-After` (`not_before`), uncounted; another failure is retried after a backoff, and fails the job at `importer.Params.MaxFailures` in a row; a refused token fails it at once.
  - Only `until` = the cutoff is asked of the source; `SaveImport` reads the cutoff again and decides. An event the importer's checks refuse (unfinished, out of bounds) is left and counted invalid; Aximote's fuel stops are left uncounted. A tracks' export not understood leaves the trips without their track.
  - What Aximote's spec leaves open (a charge's state of charge from its battery energies, its times, the export's format, the quotas: ADR 0036's B1 to B4) is an assumption, in `internal/importer/convert.go` and `internal/aximote`: a mismatch on a real account is fixed there, and a new import replaces the rows.
- **Aggregates** (`core.Summarize`, `GET /api/v1/vehicles/{id}/stats`) are computed on each request from the derived tables: no aggregate table, no cache, nothing to keep in step with a rebuild.
  - An event counts once, in the interval that holds its `start.after`, in the requested time zone. Never by overlap (counted twice) nor pro rata (the bounds do not tell when a limit was crossed). The lists filter by overlap: the difference is told in the interface ("started in the period").
  - Intervals are days, ISO weeks (Monday) or months, from calendar arithmetic in the time zone (`time.Date`, `AddDate`), never by adding hours: a day lasts 23 or 25 hours. Empty intervals are present, at zero. More than `core.MaxBuckets` (400) is an error.
  - A sum covers the known values and counts the events that lacked one (`_unknown`); a sum over nothing is 0, an average (consumption, loss per day) unknown. Durations are sums of `{min, max}` of the observed events, as the front end shows each one; reconstructed events have none and are counted apart. The two energy estimates of a charge stay apart.
  - A plug-in hybrid's (the vehicle's `model.powertrain`, read from its latest details) has no consumption, in the totals, the intervals or the bands (`core.Summary.WithoutConsumption`), and its trip page shows none: its trips' energy is the battery's alone, and nothing tells which kilometres the engine drove (ADR 0041 §3). Their fuel (`fuel_l`, from the trip meter) is still to come.
  - The distributions (`trips_by_distance`, `charges_by_soc`) cover the period, never an interval: by interval they would repeat their bands hundreds of times. Observed events only: a reconstructed trip may hold several, a reconstructed charge's SoC are readings around it; both are counted apart (`left_out`). The SoC are counted per point, so that the front end tells "below 20 %" from "at 20 %" whatever bands it draws.
  - The charges by place (`charges_by_place`) cover the period too, grouped by the place their cost takes (`core.PlaceOf`: a place marked without a position takes the AC charges and those of unknown type without one), then outside every place by type, then without a position. Reconstructed charges are counted, apart in each group: their energy adds up however many charges they hold, so the groups add up to the totals. The list of the charges, its CSV file and the statistics take a group as `place` (a place's ID, `outside`, `no_position`; `core.ChargesAt`, the same `placeIndex`): the statistics then count that group's charges only, without the orphaned costs, while the trips, the parked intervals and the odometer stay every event's. A charge's place is computed, not stored, so SQL cannot filter by it: the store reads the list's page in batches (`chargePage`, `chargeBatch`) in the page's order, keeping the group's charges until the page is full, within one snapshot; a place the account lacks keeps none.
  - The loss while parked is the drop of SoC between consecutive events (trips and charges, by `start.after` then `detected_at`), counted where the next one starts: a rise below `MinChargeSoC` is noise, a larger one makes it unknown. The store gives the latest event before the period with it (`PeriodEvents`, one transaction), for the first interval.
  - The odometer (`odometer`): at the ends of the period and of each interval, from the events' readings (a trip's at start and end, a charge's at end), never from the snapshots. It moves only while driving and every trip is an event, so the highest reading of the events before an instant holds until the next trip: an interval starts at the previous one's end (the latest event before the period for the first), else at the lowest reading of its own, and ends at the highest of those that started before its end. Its `distance_km` is end − start, not the trips' sum.
  - `runsten-api` imports `time/tzdata`: the time zones depend on neither the image nor the host.
- **Series** (`GET /vehicles/{id}/series`, `core.Runs`): the energy states a vehicle gave within `[from, to]`, both ends included, from the snapshots of the energy state (`Deriver.Readings`, `store.SnapshotsBetween`), never from the derived tables. A response is two readings, at `fetched_at` and again at `checked_at`; one across `from` or `to` gives its value at that edge, which it held all along. Nothing is interpolated: the readings come in runs, a new one where more than 90 minutes (`seriesGap`, longer than a read every hour) separate two responses, and a chart breaks its line between runs. At most 7 days and 20,000 responses (`400` beyond, never downsampled); the history limit applies, as to the statistics. How close the readings are is the collector's doing, not a limit of the API: a chart that needs them close (a charge's curve) says when they are too few, rather than a limit of the account.
- **Health** (`GET /vehicles/{id}/health`, `…/health/tyres`, `core.Health`): the tyres (each one's pressure and warning, the recommended pressures), the service (its state, the days or months and the distance left) and the checks (the fluids, the low voltage battery, each exterior light), read from the snapshots of the kinds each normalizer names (`HealthKinds`: Volvo's tyres, warnings, diagnostics, brakes and engine; the Polestar's health domain), never from a table of their own: nothing to rebuild, and a correction of a normalizer applies to the whole history. Each response covers what it reports (`Covers`, and its checks one by one), merged as the snapshots (`LatestHealth`). A warning's `NO_WARNING` is none, `UNSPECIFIED` unknown (a check reported so stays, unknown, so that nothing reads it as fine), missing not reported, every other value a warning. The pressures over a window are runs as the series' (`core.TyreRuns`, 90 minutes, nothing interpolated), at most 366 days and 20,000 responses, the history limit applied. Assumption: the Polestar's tyre fields (`<wheel>TyrePressureKpa`, `recommended<Axle>TyrePressureKpa`, `tyrePressure<Wheel>Warning`) were never seen in a response, in `internal/polestar/health.go`.
- **Row-level security.**
  - Every table carries `account_id`, with composite foreign keys `(account_id, id)` and an `account_isolation` policy.
  - The pool runs `SET ROLE runsten_app` on connect. Each transaction sets `runsten.account_id` (`set_config(..., true)`). Always go through `store.inAccount`.
  - RLS is not `FORCE`d: `SECURITY DEFINER` functions (`runsten_create_account`, `runsten_single_account`, `runsten_poll_targets`, `runsten_stale_connections`, `runsten_api_calls`, `runsten_last_pass`, `runsten_mqtt_brokers`, `runsten_user_by_name`, `runsten_session`, `runsten_has_users`, `runsten_claim_import`) run as the table owner and bypass it on purpose, with a fixed scope (one row by username or token hash, or identifiers only).
  - Each new table gets an isolation test, following `TestAccountIsolation`. `TestEveryTableIsIsolated` checks the migrated schema: every table has RLS enabled and an `account_isolation` policy on `account_id`.
- **The account's export** (`GET /account/export`, `store.ExportAccount`), every account's, whatever its limits: every table of the account, row by row as `to_jsonb` writes it (times in UTC, without `account_id`), in one read-only snapshot, streamed; its `schema` is the latest migration. The status goes with the first byte: a failure after it truncates the document. Every table of the schema is in `exportTables` or in `notExported` with a reason, and every `bytea` column of an exported table (where the secrets are) is omitted: `TestExportCoversEveryTable` fails otherwise. A new table or a new secret column updates them. An extension adds its own schema's tables after the core's (`api.ExportTable`, qualified by their schema), read in the same snapshot under the same row-level security. The core has neither terms to accept nor a deletion of the account: a self-hosted instance is its owner's, who starts a new one to start afresh, as with TeslaMate; a hosted build adds them through its extensions.
- **CSV files** (`GET /vehicles/{id}/trips.csv`, `…/charges.csv`, `internal/api/csv.go`): the items of the lists, flattened, every one of a period (`from`, `to`, filtered as the lists, the history limit applied), read at once (`EventQuery.Limit` zero: no limit) and written oldest first. RFC 4180 (CRLF), UTF-8 without a BOM, a header row named after the JSON fields, times RFC 3339 in UTC, a decimal point, an empty cell for an unknown value, a charge's cost in major units with the currency's digits. A text cell (a place, an address, a note) that begins with `=`, `+`, `-`, `@`, a tab or a carriage return is prefixed with `'` (CSV injection). `AccountLimits.NoCSV` refuses them (`403 feature_unavailable`, `csv` in the session's `unavailable`), and the front end then hides the button; the account's export stays open to every account. The front end links to them (`features/export-events`), never fetches them.
- **Vehicle models.** The catalog lives in the binary, not in the database: `vehicles` stores only the user's choice (`variant_id`, `ac_max_kw`, no foreign key); the variant in effect is recomputed on each read (`vehicles.variant_in_effect` is a copy the collector writes after each poll, for readers that have only SQL: the API never reads it), and a choice that no longer holds (variant gone, other family, other powertrain) is ignored, never an error. So an entry of `variants.yaml` is corrected, never removed, and its `id` never changes. Every figure is backed by a source (`manufacturer` or `secondary`); variants no reading tells apart name each other in `ambiguous_with` (`TestAmbiguousPairs` lists them). The onboard charger in effect is the stated one while it is one of the variant's, else the more powerful (an optional 22 kW one): an upper bound never narrows a cost by mistake. A variant has a `powertrain` (`electric` when left out, `plugin_hybrid`): a vehicle is matched, offered and chosen among the variants of the powertrain it reads (`catalog.Reading.Powertrain`, `Catalog.Offer`), never one whose powertrain is unknown or `other`, so that a hybrid's capacity is never taken for an electric's. A variant without DC charging (most plug-in hybrids) has no `dc_max_kw`, `null` in the API.
- **A vehicle's deletion** (`DELETE /vehicles/{id}`, session only, `store.DeleteVehicle`; the vehicle's settings, behind a confirmation): every table of a vehicle references it `ON DELETE CASCADE`, so its history goes with it in one transaction; a new table with a `vehicle_id` must too, an extension's as well (`TestDeleteVehicle` checks every table of the schema that has one). Its connection stays, for the account's other vehicles; listed again (`AddVehicle`), it comes back as a new vehicle, without its history.
- **Migrations**: `internal/store/migrations/NNNN_name.sql`, applied in order, in one transaction, under an advisory lock. Never edit an applied migration: add a new one. An extension's tables live in their own PostgreSQL schema, with their own bookkeeping, migrated after these, under the same rules (RLS, isolation tests).
- **Secrets.**
  - OAuth tokens (access and refresh) and an account's application key (`connections.api_key`, migration `0011`) are encrypted with `secretbox` (AES-256-GCM, bound to the account ID). The key comes from `RUNSTEN_TOKEN_KEY` and is never stored.
  - An application key is never returned by the API (its last four characters and when it was given only), never exported, never logged, and never on the debug page (which shows whether a vehicle reads with its own key, the instance's, or none). `runsten_poll_targets` gives the collector when it was set and whether it was refused, never the key: the collector reads it within the account (`ConnectionKey`).
  - A Polestar connection (migration `0023`, `provider` `polestar`, one per account beside the Volvo ID) is the owner's credential of the Data Portal (`connections.credential`: its client ID, secret and account ID, one JSON value), sealed bound to the account and to its column (`credentialData`): never returned, exported or logged; in plaintext its last four characters (`credential_last4`) and `credential_set_at`. Its access token is never stored: the collector asks for one with it and keeps it in memory. `runsten_poll_targets` gives the provider, when the credential was set and whether it was refused, never the credential: the collector's `Source` reads it within the account (`PolestarCredential`).
  - It is given by `PUT /connection/polestar` (session only, the three values in the body, never in a URL), held back by the extension's `Admission` (`403 not_admitted`), then checked by a token and the listing of its VINs (`api.PolestarVehicles`, `runsten-api`'s adapter of the client): refused (`400 credential_refused`), reading no vehicle (`409 no_vehicle`), the Data Portal unreachable (`502 source_unavailable`) or the account over `MaxVehicles`, counted over all its vehicles (`409 too_many_vehicles`), it is not stored; else its VINs are added (`AddVehicle`). `GET /connection` gives its `last4`, `set_at`, `expires_at` (90 days later, an assumption) and `refused_at`. `DELETE` erases it and keeps the connection, its vehicles and their history (migration `0024`: a Polestar connection may have no credential), which the collector no longer reads (`CredentialSetAt` zero) until another.
  - An import's token (`import_jobs.token`) is sealed the same way, bound to the account and to its column (`importTokenData`), and erased as soon as the job ends, done or failed: never returned, exported or logged. It only travels in a request's body, never in a URL.
  - The client secret only goes to the token endpoint, from the backend. Tokens, codes and secrets never appear in logs, errors or pages.
  - Never write real tokens, API keys or VINs to the repository (trivy scans for secrets).
- **Tokens.**
  - A refresh runs under the connection's row lock (`UpdateCredentials`, `SELECT … FOR UPDATE`), re-reads the credentials, and the new tokens are committed before the access token is used. With rotation, two concurrent refreshes would invalidate each other (`TestConcurrentRefresh`).
  - A lost grant (refresh refused, refresh token unused for 7 days, no refresh token) sets `reauth_at`/`reauth_reason`: the collector no longer polls the connection until a new authorization, which clears them.
  - Unknown Volvo ID behavior (error codes, lifetimes) is isolated: `reauthCodes` in `volvo`, `oauth.Params`, the simulator's `OAuth`.
- **Debug page**: it shows VINs and locations. Bind it to loopback only. What a user needs to know of the collection goes through `collector_status` and the Connection page instead.
- **Collector status** (migration `0008`): after its passes the collector writes, per vehicle, what the user is told (`collector.Status`: latest pass, mode, latest successful call, next call due, pause, quotas, latest failure as a kind, never a message). Written when it changes, else every `statusEvery` (1 minute), so that `passed_at` tells whether the collector runs; a zero `ReadAt` or `Failure` keeps the stored one, which a restarted collector does not know. Neither derived from the snapshots nor derived from: never rebuilt. `api` reads it with the vehicle (`collection`), under RLS.
- **Exposure.** A non-loopback listen address is warned about, unless `RUNSTEN_ACCESS_RESTRICTED=true` declares that the deployment only lets it be reached through the host's loopback or an https reverse proxy (`httpserver.WarnIfExposed`). `compose.yaml` sets it because its containers listen on `0.0.0.0` but publish their ports on the host's `127.0.0.1` only (the `mqtt` profile's Mosquitto, anonymous, too); keep that true when editing it. PostgreSQL is never published, and sits on an `internal` network.
- **Database user.** In Compose, Runsten connects as `runsten`: owner of the database, neither superuser nor `CREATEROLE`. `runsten_app` is created beforehand by `deploy/postgres/init-runsten.sh`, with the admin option. A migration must therefore not need more than the database owner's rights (no `CREATE EXTENSION` of an untrusted extension, no new role); `task compose-test` applies them as that user.
- **Users and sessions** (`internal/auth`, migration `0004`).
  - A user belongs to an account; one user per account for now (`users_one_per_account`). The first one is created by `runsten-api user create`, in the single account: no default account, the password is read from stdin, never from an argument or a variable.
  - Passwords: at least 15 characters, argon2id (OWASP parameters), PHC string; verification in constant time, with a decoy hash for unknown users; at most `MaxHashing` concurrent hashes.
  - Sessions live in PostgreSQL, under RLS. The cookie holds a 256-bit random token; the database only its SHA-256. 30 days absolute, 7 days idle, `last_seen_at` written at most hourly. A new password deletes the user's sessions.
  - Cookie: `HttpOnly`, `SameSite=Lax` (sent back on the redirect from Volvo ID), `Path=/`; `Secure` with the `__Host-` prefix when the redirect URI is https.
  - Throttling: 10 failures in 15 minutes per username or per peer address, in memory.
  - Cross-site requests that change state are refused by `http.CrossOriginProtection`. The account comes from the session, never from the request.
  - An extension may sign users in otherwise (an identity provider, with sign-up on a first sign-in): it opens the same sessions (`auth.Service.Open`). Do not build a provider sign-in, signup or password recovery here.
- **Personal access tokens** (`internal/auth/token.go`, `internal/api/tokens.go`, migration `0014`): a program reads the API with one, without a session.
  - `rst_` then 256 random bits in base64url, shown once when issued; the database keeps its SHA-256 (`api_tokens`, RLS, `runsten_api_token(hash)` to find it before the account is known). A name, an expiry (30, 90, 365 days or none), `last_used_at` written at most hourly. An expired token stays listed until revoked; a new password leaves the tokens, the user's deletion takes them.
  - `Authorization: Bearer` is checked before the cookie, and alone: an invalid header is a 401 (`WWW-Authenticate: Bearer error="invalid_token"`) whatever the cookie. A token serves the `GET` operations (`operation`) only; the others answer `403 insufficient_scope`, and so do those of the session and of the tokens (`sessionOperation`), which a token can neither read nor manage. In memory, each token makes at most `tokenBurst` (120) requests at once, then `tokenRate` (2) per second (`429 rate_limited`).
  - The account's limits apply to a token as to the session: it reads what the web interface shows, nothing more.
  - `api.Server.ServeAs` serves a request as an account's user, without credentials, for an extension that authenticated the user itself (an assistant's connector built on the JSON API): treated as a token, so it reads only.
- **MQTT broker** (migration `0016`, `internal/api/mqtt.go`): one per account, in `mqtt_brokers`, given in the settings (`GET`/`PUT`/`DELETE /mqtt`, session only), never by the environment. The collector publishes the vehicles' state to it (see "Publication" under "Collector behavior"); `mqtt_status` is what it writes of its connection, a kind of failure, never the broker's message, deleted with each new configuration.
  - The password is sealed by `secretbox`, bound to the account and to its column (`mqttPasswordData`): never returned (`password_set`), exported or logged. A `PUT` with `password` null keeps it for the same host only: for another, it must be given again, or whoever holds the session would read it there.
  - `RUNSTEN_MQTT_PRIVATE_BROKERS` (default true; false for an instance open to the public): when false, `mqtts://` only, and no loopback, private, link-local or reserved address (`netguard.Public`), nor `localhost` or a single label; `PUT` refuses what the URL tells (`400 broker_refused`), the collector checks the resolved addresses again when it connects. `public_only` tells the interface.
  - `AccountLimits.NoMQTT` refuses the `PUT` (`403 feature_unavailable`, `mqtt` in the session's `unavailable`); the broker set before stays, readable and removable.
  - The collector lists the accounts with a broker through `runsten_mqtt_brokers()` (migration `0017`: the account and `updated_at`, nothing else), then reads the configuration and the password within the account (`PublishBroker`). It writes `mqtt_status` only for the configuration it connected with (`updated_at` unchanged): a status of the previous one never shows on a new one. A zero time keeps the stored one.
- **`runsten-api`** requires a session on every route but the sign-in and `/healthz`. `/auth/volvo/start` binds the flow to the session's account; the callback requires the same account. The OAuth `state` is single use, expires after 10 minutes and is bound to the browser by a cookie; the only redirect target is the configured Volvo ID. Redirects and links are relative, so that a reverse proxy may add a prefix. It serves plain http: beyond loopback, an https reverse proxy (see Exposure).
- **`runsten-web`** serves the interface and relays `/api/`, `/auth/` and the OAuth metadata (`/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`, which `runsten-api` answers 404 to in this build) to `runsten-api` at the same origin: the session cookie and `CrossOriginProtection` work unchanged. The relay keeps `Host` (`Out.Host = In.Host`), or `runsten-api` refuses the `POST`/`DELETE` of a browser without `Sec-Fetch-Site`; `RUNSTEN_WEB_API_HOST=api` sends `runsten-api`'s own host instead, for a platform that routes by `Host`; relayed responses keep `runsten-api`'s headers. Its own responses carry a strict CSP (`default-src 'none'`, `script-src 'self'`, styles by a nonce drawn per response and written into `index.html`, which Vuetify's theme `<style>` reads from `meta[name="csp-nonce"]`), `nosniff` and `no-referrer`; with `RUNSTEN_WEB_NOINDEX=true`, every response, relayed or not, `X-Robots-Tag: noindex, nofollow`. The files are read from disk (`RUNSTEN_WEB_DIR`), not embedded: the Go module builds and tests without the front end. `RUNSTEN_WEB_BASE_PATH` goes into `<base href>`; the front end resolves the API and its routes against `document.baseURI`, never against `/`. The Volvo redirect URI is on `runsten-web` (port 8082 in Compose).
- **A vehicle's connection** in the API (`connectionJSON`) names its `provider`: a Volvo's has `api_key` and the Volvo ID's times, its `credential` null; a Polestar's has `credential` (`set`, `refused`, `missing`), its `api_key` null, and `status` always `active`. `unshared_at` is a Polestar's no longer shared, as `market_refused_at`. A Polestar of the Data Portal has no family: `offered` takes its brand (`core.Snapshot.Brand`), `variants` lists the brand's (`catalog.Brand`), and the variant in effect sets its `family`; `PUT …/model` checks a choice by `catalog.Chosen`.
- **JSON API** (`/api/v1`): built with huma (`humago`, on the `ServeMux` of `runsten-api`). The source of the contract is the code of `internal/api`: its operations (`huma.Register`) and their input and output types, whose tags carry the documentation (`doc`), the constraints (`minimum`, `pattern`…) and the enumerations (a `Schema` method built from the domain's values). `api/openapi.yaml` is generated from it; with the golden files `internal/api/testdata/*.json`, it makes a change of the contract visible in the diff. Every object has `additionalProperties: false` and lists all its properties as `required` (huma's default). A nullable object is a `null[T]`: huma describes nullable scalars (`*float64`) only. huma ignores the fields of an unexported embedded struct: embed exported types (`EventFields`) or repeat the field. Errors are always `errorJSON`: `newError` maps huma's own (422, 413) to the contract's 400. Times of events stay bounds, `reconstructed` is kept, unknown values are `null`. Event IDs are the detection time to the microsecond, stable across rebuilds; an imported event's is `source:source_id`. Every event has `sources` and `imported`: one field of provenance for the derived events and the imported ones (ADR 0035 §8). Lists are newest first with keyset cursors. Errors: `{"error": {"code", "message"}}`.

## Collector behavior

- Modes: parked, driving and charging. They are derived from engine-status (`RUNNING`) and the charging status (`CHARGING`).
- Intervals: parked 10m, active 1m, rare 1h (location, odometer, diagnostics, brakes, engine, fuel, tyres, warnings, doors, windows), details 24h. When a trip or charge ends, or a charge starts, location, statistics and odometer are fetched right away.
- Optional endpoints (`optional`: brakes, engine, fuel): their scope may be missing from an application or an older grant, or the model may lack them. A 404, or a 403 that is neither the quota nor a refused key (assumption: a missing scope), is no failure told to the user: the endpoint is left out for a details interval (`vehicleState.missing`, in memory, apart from `next`, which a transition brings forward), logged once until it answers.
- Tokens: asked once per vehicle pass from the `TokenSource`, refreshed `oauth.Params.Margin` before expiry; idle connections are refreshed every `KeepAlive` (1 day) so that their refresh token (7 days) does not lapse.
- Application keys: Volvo counts its quota on the application of the key (`vcc-api-key`) a call is made with, not on the OAuth client of the token (tried on the real API). The instance's key (`RUNSTEN_VOLVO_API_KEY`, optional) reads every connection, and an account may not give one (`409 instance_key`; a key left in the database is ignored). Without it (`Quota.NoInstanceKey`), each connection reads with its own key; one without is not read, nothing is due, and it is logged once. A key never reads another account's vehicles, and never stands in for another whose quota ran out. The token refresh and the keep-alive do not depend on the key.
- The Volvo application is optional (`RUNSTEN_VOLVO_CLIENT_ID` and `_SECRET` together, or neither): without it, `runsten-api` refuses `/auth/volvo/*` and the account's key (`volvo_not_configured`, `volvo: false` in the connection settings) and the collector calls nothing of Volvo (`Collector.WithoutVolvo`: no poll, no token, no keep-alive, which Volvo would refuse and the grant be taken for lost). `RUNSTEN_APP_URL` is the address users open: its scheme makes the cookies Secure, and the redirect URI defaults to it + `auth/volvo/callback`; an instance with `RUNSTEN_VOLVO_REDIRECT_URI` alone works as before.
- Errors:
  - quota (403 "Out of call volume quota") → that API is blocked until `RetryIn`, for the key it was called with. It is never an authentication error;
  - key refused (401 or 403 whose message names the key, `volvo.KindKeyRefused`; observed: the gateway's 401 "Access denied due to invalid VCC-API-KEY", or "missing header VCC-API-KEY"; keys of applications created the same day were refused about one call in two, at random, so the client makes a call up to `keyAttempts` (3) times while its key is refused) → no refresh, the grant and `reauth_reason` untouched; the key is tried again after `keyRetry` (1 hour); a connection's own key refused `keyRefusals` (3) times in a row, nothing read in between, is marked refused (`api_key_refused_at`) until the user sets another (observed: a key minutes old refused on the 3 attempts of a call within its first hour, while it read the other endpoints); failure kind `key_refused`;
  - market (404 whose message is "Vehicle does not belong to allowed markets", `volvo.KindMarket`; observed on energy-state only, every other endpoint, the details included, answering a plain 404 "NOT_FOUND" for the same vehicle, which stays `KindNotFound`) → the vehicle is marked (`vehicles.market_refused_at`, migration `0022`, `Target.MarketRefused`) and no longer polled, nothing due; the vehicles listed again (a new authorization of the Volvo ID, a new key: `store.AddVehicle`) clear the mark; failure kind `market`; the API gives `market_refused_at` with the vehicle;
  - 429 → the account is paused;
  - 401 → the token is refreshed once and the call retried; a second 401 pauses the account for one parked interval;
  - lost grant → the connection is skipped, logged once, and shown on the debug page.
- Quota budget (`budget.go`): the Volvo quota (`Quota.Daily`, `RUNSTEN_VOLVO_DAILY_QUOTA`, 10,000 calls a day per API and key; assumption: over any 24 hours) is counted on a unit: the API of a connection's own key, or the API of the instance's key (default: every account without its own shares it), or the API and the account on the instance's key with `Quota.PerUser` (`RUNSTEN_VOLVO_QUOTA_PER_USER`), should Volvo count it per Volvo ID; the agreement does not say. A quota refusal (403) blocks its unit too. A token bucket per unit spreads 90 % of the quota (`quotaReserve`: `runsten-api`'s enrollments, and the calls of a pass a crash loses) at a steady rate, up to one hour's worth at once (`budgetBurst`). A due call the budget defers stays due; every call made is counted, the retry of a rejected token included. Each pass polls the accounts that called the least lately with the instance's key first (usage halved every `usageHalfLife`, 6 hours): the one that asks less is served in full, the rest goes to the others. The calls with an account's own key count in no one's usage.
- Calls (migration `0010`, `api_calls`): the budget's calls, per account, API and hour, saved after each pass (even a canceled one; kept for the next pass when the save fails) and kept 30 days. The first pass replays the last 24 hours (`runsten_api_calls`, across the accounts), each hour's calls taken at its end, on the key each account's connection has now: a restart neither spends the budget again nor forgets who called the most. It fails, and polls nothing, while they cannot be read.
- Health: with `RUNSTEN_HEALTH_ADDR`, `/healthz` answers 503 once no pass could list the vehicles for 15 minutes (`healthMaxAge`; `Run` calls its `passed` callback after each such pass). `runsten-collector healthcheck` probes it. A liveness probe restarts a collector that fails it, which starts its heartbeat again: an uptime monitor reads `runsten-api`'s health report instead (`GET /healthz/full`, with `RUNSTEN_HEALTH_TOKEN` as a bearer token, `health.Reporter`), whose `collector` check is the latest `passed_at` across the accounts (`runsten_last_pass`), stale after the same 15 minutes, and whose `database` check fails beyond 80 % of the server's connections (`pg_stat_database`: `pg_stat_activity` hides the other roles' backends from `runsten_app`). `?check=name` runs one alone, so that a monitor watches each part apart; the details are never public, nor any error's text.
- Publication (`internal/publish`, `publish/mqtt`, ADR 0032): after `Deriver.Update`, each vehicle whose pass saved a snapshot is given to the `Publisher`, which reads its state as `GET /vehicles/{id}/state` does (`Deriver.Current`).
  - The topics are a versioned contract, like the API: `<prefix>/vehicles/<vehicle id>/battery_level`, `range_km`, `charging_status`, `plug`, `charge_type`, `charging_power_kw`, `target_soc`, `odometer_km`, `engine`, `location` (JSON, emptied unless `publish_location`), `read_at`, and for a vehicle read with a credential (the Polestar Data Portal's) `credential_status` (`publish.Credential.Status`: `valid`, `expiring` from `publish.RenewAhead` before its expiry, the web's `renewAhead`, `expired`, `refused`, `missing`) and `credential_expires_at`, built at every `Sync` from the store (`PublishCredentials`), since a refused credential reads nothing that would publish them; then the health's (`publish.Health`, read as `GET …/health` does): `tyre_pressure_<wheel>_kpa`, `tyre_warning` (the worst of the tyres: a known one whatever the others, `ok` only when the four are known), `service`, `service_days`, `service_months`, `service_distance_km`, `warning_<check>` of the fluids and the battery and `warning_lights` (any light; `ok` only when every light reported is known), `warning` or `ok`; then the climate's: `outside_temp_c`, `cabin_temp_c`, `climate`, `preconditioning`, `battery_heater` (`on` or `off`); plain text, QoS 1, retained; an unknown value is an empty retained message, which removes the previous one, never a zero. `<prefix>/status` is `online` or `offline` (the testament). Changing one is a new version of the contract, documented.
  - One paho connection per account with a broker, opened by `Sync` at the start of each pass, closed when the configuration goes, changes (`updated_at`) or the policy gives the account `NoPublish` (`collector.Reads`); the binary closes them all when it stops. As it closes, a connection that is up removes what the next configuration will not replace (`cleanupFor`): everything when the broker is removed or moves to another URL; the entities' configurations when the discovery is turned off or moves to another prefix; the values and the availability when they move to another topic prefix. Else, and under `NoPublish` or a stop, it publishes `offline` (the broker drops the testament on a clean disconnection): the entities stay, unavailable, and come back as they were. A connection down removes nothing. paho opens a lost connection again with a growing delay; a failed first attempt is tried again by the following passes, 30 s then doubled up to 10 minutes. Client ID: the configured one, else `runsten-` and 15 hex digits of the account (23 characters, what every 3.1.1 broker accepts).
  - Every publication runs in the collector's goroutine. paho's goroutines only record what happens to the connection (connected, failed, lost), which the next `Sync` or `Publish` acts upon: a new connection gets `online` and the latest state of every vehicle the publisher knows, then only the values the broker has not acknowledged. A vehicle's first state goes out with its first pass that saved a snapshot.
  - Failures are kinds (`unreachable`, `refused_address`, `tls`, `not_authorized`, `rejected`), logged on a change with the account only, never the broker's message nor the URL, and written to `mqtt_status`; they never stop the reads. Any failure of the TLS handshake once TCP is up is `tls`: a certificate refused, or a port that does not speak TLS.
  - The dialer is the publisher's own (`SetCustomOpenConnectionFn`): paho's would follow a proxy from the environment around the address check. With `RUNSTEN_MQTT_PRIVATE_BROKERS=false` (read by both binaries), `mqtt://` is refused before dialing and `net.Dialer.Control` refuses every resolved address that is not `netguard.Public`. TLS verifies the broker with the system's authorities, at least TLS 1.2. Default ports 1883 and 8883.
  - Home Assistant's discovery (`discovery`, ADR 0032 §8): per entity, a retained configuration under `<discovery prefix>/<component>/runsten_<vehicle id>/<object>/config`; sensors (battery, range, charging status and charge type as enums, charging power, charge limit, odometer, last read, the four tyre pressures, the service as an enum, its days, months and distance), binary sensors (plug, charging, engine; the tyres and each warning as a `problem`, on for any word but `ok`, declared for every vehicle, unknown where it reports nothing, a Volvo's pressures; and the credential's problem, on unless `valid`, with its expiry as a diagnostic timestamp, both configured only for a vehicle read with a credential, emptied for the others; the climate's five, its temperatures and three binary sensors, configured only for a vehicle that tells it, `publish.Model.Climate`, the snapshot covering `FieldClimate`), a device tracker on `location`'s attributes (its configuration emptied unless `publish_location`). One device per vehicle (`runsten_<vehicle id>`), named as the web interface labels it but never by its VIN (`publish.Labels`: the variant, else the family, with the model year; before the details, `Volvo` and 6 characters of its ID; two alike end with 6 characters of their ID), its availability `<prefix>/status`. Sent before the values, on each connection then when they change (a label changes when a vehicle alike comes or goes). The configurations are a contract too: `internal/publish/testdata/discovery.json` (`go test ./internal/publish -update`). Checked against Home Assistant 2026.9 (its container, the golden file's configurations published by hand): a sensor ignores an empty payload, or refuses it with a warning (an enum, a timestamp), and takes `None` for unknown, so the templates turn an empty value into `None`; a device tracker keeps its position on attributes without one and drops it on null coordinates, which an empty `location` becomes. Check again when a template changes: the CI runs no Home Assistant.
  - A vehicle gone from the account (`Sync` gets every account's vehicles, those the policy leaves unread included) has its configurations and values emptied at the next flush. A publisher restarted knows nothing of the vehicles removed before.
- The Polestar Data Portal (`Source`, `polestarsource`, migration `0023`): each vehicle is read through its connection's provider (`Target.Provider`). Volvo's reading is unchanged.
  - Paces: parked, the battery and the availability every parked interval, the odometer, the position and the target level every rare one; driving or charging (the availability's `usageMode`, a charge active in the battery), the four telemetries every active interval; the health every rare interval in every mode. The odometer and the position are read at once when a trip or a charge ends, or a charge starts.
  - The access token is asked for with the credential at the first call due, kept until a minute before it expires, asked for again once on a 401; rejected again, the connection waits a parked interval. A failure to ask for one waits `loginRetry` (1 minute), failure kind `token`.
  - Refusals: the credential refused (401 on `/token`, or `AUTHZ_CLIENT_ID_MISMATCH`) marks the connection (`credential_refused_at`) until the user sets another, failure kind `credential_refused`; a VIN no longer shared (`AUTHZ_VIN_UNAUTHORIZED`) marks the vehicle (`vehicles.unshared_at`) until it is listed again (`AddVehicle`), `unshared`; a domain not granted is left out for a details interval, `not_granted` (an optional one, `EndpointSpec.Optional`, the health, is told to no one); `DATA_NOT_AVAILABLE` for a rare interval, told to no one; a 429 pauses the connection until `Retry-After` (else a minute).
  - Quota: 10,000 calls a day per credential, over every domain (API `polestar` in `api_calls`), budgeted as an own key's: a unit of its own, in no one's usage.
  - Logs that measure the Data Portal on real cars, its behavior being assumed (`Source.Upload`), never with the VIN nor any value: each new upload of the car per domain (`vehicle upload`: `sent_at`, its `age` when read, `received_after`, `since_previous`, the `mode`), the paths of a domain's fields when they change (`upload fields`, with the model year), a 401 on `/v1` with the access's age (`access rejected: asked for again`), a 429 with the connection's calls of the last minute and its budget left. The API's errors carry their limit headers (`Retry-After`, `*ratelimit*`, `x-amzn-ErrorType`), and the VINs of its messages are masked.
- Tesla's Owner API (`teslasource`, migration `0025`, ADR 0040 §4): the connection is the owner's refresh token, kept as a Polestar credential is (`connections.credential`, sealed, its last four and its time in plaintext).
  - Access: at the first call due, a refresh, the refresh token given in exchange stored before the access is used (`RotateTeslaToken`, only over the token set at the same time: one the owner set since is left alone); not stored, it is kept in memory and refreshed with until it is, the one stored perhaps no longer refreshing. Then `/products`: the vehicles are read by Tesla's identifier, not their VIN, looked for again once when a VIN is missing, then marked `unshared`. The access lasts its `expires_in` (8 h).
  - Paces of its own (`SourceSpec.Intervals`, `teslasource.Intervals`, not `RUNSTEN_POLL_*`): the car's state (`vehicle`, which does not wake it) every minute but driving; `vehicle_data` every minute parked or charging, every 15 s driving, and at once when a trip or a charge ends. Quota: 3,000 calls a day per refresh token (API `tesla`), a prudent cap, the real limit unknown.
  - Sleep (`EndpointSpec.Awake`, `SourceSpec.Sleep`, `Activity.Asleep`): `vehicle_data` keeps the car awake, so it is read only while the car is seen awake (`online`; `asleep` and `offline` alike, a 408 too, kind `KindAsleep`, which is no failure and puts the car parked), and once parked and awake for 3 minutes it is left alone for 15 (the sleep window), the state still read; a car seen waking up closes the window. Starting a trip in the window is seen at its end, derived from the odometer. Volvo and Polestar have neither.
  - The flag `source.tesla` (ADR 0039, F4): an account it is off for gives no token (`PUT /connection/tesla`, 403 `feature_unavailable`), has no Tesla tab, and its Teslas are no longer read (`collector.SetGate`, asked once per pass and account), their token and history kept.
  - Refusals: `invalid_grant` or `login_required` marks the connection (`credential_refused`); the 403 that sends to the Fleet API too, failure kind `api_closed` (`KindAPIClosed`); a 401 asks for a new access once; a 429 pauses the connection until `Retry-After` (else 5 minutes).
- Do not invent Volvo API behavior. When something is unknown or assumed, say so in a comment ("assumption"), and make it a named parameter if it drives logic.

## Simulator

- Application keys: any key is accepted, each with its own quota; `SIM_API_KEYS` (comma separated) accepts those only, and refuses another, or none, with the gateway's observed 401 ("Access denied due to invalid VCC-API-KEY", "… missing header VCC-API-KEY"), before any API.
- Scenarios are YAML files in `scenarios/`, with an optional `api:` section: `dailyQuota`, `perMinute`, `tokenTTL` (tokens it did not issue), `errorRate`, `latency`, `outages`, `accessTokenTTL`, `refreshTokenTTL`, `grantTTL`.
- A `vehicle`'s `usableKWh` (default: `batteryKWh`) is the capacity its SoC of 0 to 100 % runs over: every kWh ↔ SoC conversion uses it, linearly faded by `fadePerYear` (default 0) a simulated year (365.25 days) since the vehicle's own `start`; only `batteryCapacityKWH` reports the nominal `batteryKWh`, and `chargingPower` stays the power entering the battery (the derivation's `PowerSide` assumption).
- The simulated Volvo ID (`/as/authorization.oauth2`, `/as/token.oauth2`) consents at once, requires PKCE S256, rotates refresh tokens and, by default, revokes the grant when a used refresh token is presented again. Its development application is `runsten-dev` (`volvoapi.DefaultOAuth`). API faults and limits do not apply to it.
- Its grants, access and refresh tokens live in memory, lost with the process, unless `SIM_DATABASE_URL` names a PostgreSQL database of its own: `pgledger` creates its `sim_*` tables there, the simulator restores them at start and records each issue and revocation before answering (a write that fails answers 500, the token presented stays unused). Authorization codes stay in memory. The times recorded are the simulated clock's, which starts again at the scenario's `start` on each restart: the tokens recorded before simply live longer. The simulated vehicles themselves still start their scenario again.
- Precedence: defaults < scenario < `SIM_*` environment variables.
- A scenario's `marketRefused: true` is a vehicle whose market the API does not serve: listed with the account's vehicles, refused by every other endpoint with a 404, the Energy API's naming the market, as observed (the bodies' formats are assumed).
- Faults are applied before quota accounting: a failed call is not counted.
- Several vehicles: `SIM_SCENARIO` takes a comma-separated list, one vehicle per scenario, under one Volvo ID (`scenario.NewFleet`, the handler's sources keyed by VIN). VINs must be distinct. Only the first scenario may have an `api:` section: one API serves them all, and its outages count from that scenario's `start`. The clock starts at the earliest `start`; a vehicle whose scenario starts later stays parked, in its initial state, until then. The quota is counted over every vehicle (assumption: per application and API, not per vehicle). `/sim/status` lists each vehicle's progress.
- Time scale: a reading is stamped by the collector's clock, so a charge's energy from its power is integrated over the collector's time. `task run-collector` (and `tilt up`) sets `RUNSTEN_DEV_CLOCK_SPEED=60`, the simulator's speed: the collector's time runs at ×60 from the latest time a previous run reached (`devClock`), never backwards. Compose keeps real time (the e2e tests depend on it), so its battery page has no estimate.
- A plug-in hybrid (a Volvo scenario's `powertrain: plugin_hybrid`, `scenarios/v60-phev.yaml`, profile `v60-phev-like`): its details tell `PETROL/ELECTRIC`; once its battery is down to `holdSoc` (default 2 %), its engine holds it there, a point up and down (charge sustain, as a real V60); a drive's `engineChargeKWhPer100km` has the engine charge the battery meanwhile (a charge mode; its rate is an assumption). Its fuel is not simulated: the tank stays at 0 l, the fuel statistics null. `TestSimulatedPlugInHybrid` derives the scenario: its charge mode, between two parked readings, makes no charge, and would for an electric car.
- Tesla (`teslaapi`, on the same server under `/api/1/`, its token under `/oauth2/v3/token`; a scenario's `brand: tesla`, `scenarios/model3.yaml`): the owner's refresh token, `teslaapi.DevRefreshToken` (development only), is rotated on each refresh and the one given then refused (`invalid_grant`), the strictest of what Tesla may do; tokens are signed, so they survive a restart of the simulator, which accepts them all again. Access tokens live `SIM_TESLA_TOKEN_TTL` (8 h). `vehicle_data` answers the live state, but only while the car is awake: neither driving nor charging, it falls asleep `SIM_TESLA_SLEEP_AFTER` (10 min, unknown on the real car) after its last activity or its last `vehicle_data` (a read of `/vehicles/{id}` does not count), reports itself `offline` as the real one, and answers `vehicle_data` with a 408. Faults on demand: `POST /sim/tesla/rate-limit?for=10m` (429 with `Retry-After`), `owner-api?closed=true` (the 403 that sends to the Fleet API), `revoke` (every refresh token issued so far refused) and `refresh-token` (a new one, as Tesla Auth gives it). Distances in miles, pressures in bar, the shapes those of the Model Y's real responses (`teslaapi/vehicle_data.json`).
- Aximote (`aximoteapi`, on the same server under `/api/public/v1/`): one token, `aximoteapi.DevToken` (development only); `aximoteapi.Default` is an electric car with the first scenario's VIN, whose history ends a month before the simulator's start in real time (it must stay before the collector's first reading, stamped with its own clock), and a petrol car without a VIN. `LimitAfter` answers a 429, `Revoke` refuses the token: the tests' only.
- To test the collector end to end, share one `clock.Manual` between the simulator handler and the collector. See `simulatorFor`, `startFleet` (several vehicles) and `playDay` in `internal/collector/collector_test.go`, and `playFleet` in `internal/derive/polestar_test.go` (Volvos and Polestars of one account, the Data Portal under `polestarapi.Prefix`, derived as they are read).

## Front end

`web/` is the web interface: Vue 3 (`<script setup>`, Composition API), TypeScript strict (5.9: TS 7 is not yet accepted by the ecosystem), Vite, Vuetify 4, vue-router, vue-i18n, TanStack Query, `openapi-fetch`. Prefix every command with the Node of `web/.nvmrc` (`nvm use`): with another version, the ICU data differs and the Swedish formats of two tests do.

- **Contract.** The types come from `api/openapi.yaml` (`npm run gen` → `src/shared/api/schema.d.ts`, ignored by git, regenerated by every `npm run` target): the entities' models are aliases of the generated schemas. No hand-written API type, no generated client: `openapi-fetch` (`shared/api/client.ts`) turns `{"error": {…}}` into `ApiError` (`status`, `code`, `retryAfter`). A 401 outside `/session` notifies `onUnauthorized`: the app clears the cache and goes to `/login?next=…`.
- **Feature-Sliced Design.** Layers `app → pages → widgets → features → entities → shared`; imports only go down, and only through a slice's `index.ts` (ESLint `no-restricted-imports`, one block per layer; `test/architecture` checks every slice has one). Inside a slice, segments (`ui/`, `model/`, `api/`, `composables/`) import each other relatively; leaving it takes the `@/` alias, never `../../`.
  - TanStack Query lives in `features/*/composables/` only. Entities expose plain functions returning promises, and query key factories (`model/queryKeys.ts`); never an inline key.
  - Pages never import `entities/*/api`: data goes through features.
  - Entities do not import one another: what trips and charges share (`EventWhen`, `ReconstructedBadge`, `FactItem`) is in `shared/ui`.

## Tests

- Table-driven tests. They must be deterministic: manual clock, injected randomness (`Faults.Rand`).
- Store tests need PostgreSQL. `task test` starts it and sets `RUNSTEN_TEST_DATABASE_URL`, and each test gets a throwaway database.
- Coverage is computed on `./internal/...`, with a minimum of 70% (currently about 96%). Do not let it drop.
- The JSON contract of the API is in `internal/api/testdata/` and `api/openapi.yaml`, both written by `go test ./internal/api -update`; review the diff as an API change. `internal/api/openapi_test.go` checks:
  - `api/openapi.yaml` is the document of the API (`TestOpenAPIFile`);
  - every `/api/` response of the package's tests goes through `checkedAPI` and is validated against it (libopenapi-validator), errors included: huma validates the inputs, not the outputs; a route the spec does not describe must answer 404 or 405;
  - the golden files are validated, and so are their mutations (a field removed, renamed or added, a value of another type), which must all fail;
  - every response the spec declares is produced by some test (`TestMain`, on a full run of the package), and every object is strict (`TestSpecIsStrict`).
  - `task lint-api` lints the generated spec (Redocly CLI).
- **Front end** (`task web-test`): Vitest, jsdom and Vue Test Utils, in `web/test/`, mirroring `src/`, named `*.test.ts`. Components and views are mounted with the app's plugins (`mountWith` in `test/utils.ts`) and the API's golden files as fixtures (`@fixtures/*.json`, from `internal/api/testdata/`); composables are tested by mocking their entity's API module (`vi.mock` + `vi.hoisted`) with a real `QueryClient`. The locale and time zone are fixed (`en-GB`, `UTC`, `test/unit.setup.ts`). Coverage on `src/`, minimum 70% (currently about 99%). House rules: no non-null assertion (`!`), even in tests (`?.`); `beforeEach` with braces; `vi.waitFor` for a navigation; `.v-alert` rather than `[role="alert"]` (Vuetify's fields have that role too); `plain()` for the non-breaking spaces of `Intl`; `seen()` and `heard()` (`test/utils.ts`) for a text shown and read apart (`SpokenText`). jsdom has no canvas: a test that mounts a chart replaces `vue-chartjs` with `test/chart-stub.ts` (`vi.mock('vue-chartjs', () => import('@test/chart-stub'))`) and reads the props of its `Bar` or `Line`. Tests that depend on today fake `Date` only (`vi.useFakeTimers({ toFake: ['Date'] })`), so that the router's promises keep running.
- **Browser** (`web/e2e/`, `task e2e`, and `task compose-test`): Playwright and axe, on four projects (desktop 1280×800 and Pixel 7, light and dark), locale `en-GB` and time zone `UTC`. They never assert a precise time or duration: the collector of Compose stamps its readings in real time while the simulator runs at ×60. Only two projects try a wrong password: the login throttle counts failures per peer, and they all come from `runsten-web`. What is the account's rather than a project's (the DC charge's entered cost) is changed under `exclusive(name, fn)` (`e2e/support.ts`), a lock the workers share, one project at a time; a spec that needs a currency sets the euro (`setEuro`), the only one any spec chooses. Specs import `test` and `expect` from `e2e/support.ts`, not from `@playwright/test`: its `test` records the `securitypolicyviolation` events of every page, and `checkView` fails on any, with axe. `checkView` waits for the finite animations first: axe would measure a message still fading in. Screenshots of every view, and the report and traces of a failure, go to `web/e2e-results/`, which the CI publishes. Vitest never takes them, ESLint, Prettier and `vue-tsc` (`tsconfig.e2e.json`) do.
- `task test` runs with `-race` and coverage; `task test-norace` runs the same tests as the binaries are compiled, since the race detector changes the generated code (an evaluation order bug in `store.eventPage` showed only without it). Both are in `task integration`; `task test-unit` (in `task unit`) runs the tests without PostgreSQL, the store's skipped.
- `task compose-test` (part of `task system`) starts `compose.yaml` with `sim.env`, the `mqtt` profile and the `errand` scenario under its own project, creates the user, signs in, connects the simulated Volvo ID under the session, reads the state, a trip, a charge and a reconstructed trip through the API, checks that the statistics are the sums of the lists, runs the browser tests of `web/e2e/` (Playwright and axe, `scripts/e2e.sh`, in the pinned Playwright image and the stack's network), sets the account's broker to the profile's Mosquitto (`PUT /api/v1/mqtt`) and reads its retained messages with `mosquitto_sub` in its container (`online`, the state topics against the API's state, the health's words of the simulated Volvo, the 27 discovery configurations), then removes the broker and checks that nothing is left on it, then backs up, restores and rebuilds as `documentation/self-hosting/backup.md` describes. Before the browser tests it imports the vehicle's history from the simulator's Aximote through the API and reads the job's report and the imported events; the browser tests import it again first (`imports.setup.ts`, the `setup` project), read it in their four projects, then one `imports` project alone imports and deletes it from the screen once they are done. It takes about two minutes, needs curl, jq, `web/node_modules`, and ports 8080, 8081, 8082, 8090 and 1883 free. Change that procedure and the script together. `task e2e` runs the browser tests alone, against `task compose-sim` on the `errand` scenario.
- The MQTT adapter is tested against an embedded broker (`github.com/mochi-mqtt/server/v2`, test only) on the loopback, plain and over TLS with a certificate made by the test: what it retains, what it receives, the testament, a lost connection, each kind of failure. Its tests wait on paho's goroutines (`eventually`), in real time, a few seconds at most.
- For guard rails (depguard, RLS), a quick mutation check is welcome: break the rule and watch the test or lint fail.

Tools (golangci-lint, govulncheck) are Go tools pinned in `go.mod` (`go tool ...`); Task in `tools/go.mod`, a module of its own so that its dependencies stay out of the application's (`go tool -modfile=tools/go.mod task`, as the CI runs it, or an installed `task` of the same major version); the front end's, exact versions in `web/package.json` (`save-exact`, `engine-strict`). Trivy, Redocly CLI, Playwright (its version is `@playwright/test`'s: update them together) and PostgreSQL run in Docker, pinned by digest (PostgreSQL and Mosquitto in both `Taskfile.yml` and `compose.yaml`: update them together). Images are distroless nonroot, pinned by digest, cross-compiled from the build platform (`--platform=$BUILDPLATFORM`, `TARGETOS`/`TARGETARCH`), tagged `:dev` when built locally (`task image`, `sim.env`), and published by a release (`task release-images`, the workflow `release`, on a tag `vX.Y.Z`) to `ghcr.io/runsten-app` under the names `compose.yaml` pulls. They have no shell: a healthcheck is a subcommand of the binary, never `curl`.

Tilt runs the development stack only (`brew install tilt`, not pinned). The `Tiltfile` has local resources only, no Kubernetes, and calls no `local()` when it loads: Tilt refuses it under a Kubernetes context that looks like production. A new service's task gets its own resource, with `deps` on the packages it is built from (`go list -deps`).

While developing, run the tests of what changed (`go test ./internal/<pkg>/...`, Vitest on the touched files or `task web-test`) and its lint (`task lint`, `task web-lint`), and say what ran. The full `task ci` is the GitHub workflow's, whose jobs run its levels in parallel, split by what they need rather than by how long they take: `task unit` (Go or Node alone, no container: it runs anywhere; `unit-go` and `unit-web` are two jobs, each run only when its side changed, as `dorny/paths-filter` tells: the front end's side includes `api/openapi.yaml` and `internal/api/testdata/`, its types and fixtures; Go's is the code outside `web/`, the code being anything but Markdown and the repository's tooling: `LICENSE`, `.coderabbit.yaml`, the issue templates, Dependabot, the CLA's and the release's workflows), `task integration` (containers: PostgreSQL, Redocly, Trivy; the coverage threshold is checked there, over every test) and `task system` (the images and the Compose stack, browser tests included; over 10 minutes, needs ports 8080, 8081, 8082, 8090 and 1883 free: no `task compose-sim` or `tilt up` running). Integration and system run whenever the code changed, and all must pass (or be skipped) on the pushed commit. When a full run is asked for, `task unit` is the local one; run `task integration` or `task system` locally only when asked, or when a change touches what only they exercise (the store and its migrations; `compose.yaml`, the Dockerfile, `scripts/`), and tell the user first.

## Conventions

- **Language.** Code, comments, error messages, logs, README and commit messages are in English.
- **Style.** Match the surrounding code: its comment density, naming and idioms. Comments explain *why*, not *what*.
- **Git.**
  - Atomic commits.
  - Commit only when asked.
  - Never push, tag, `--amend` or force-push without an explicit request.
  - A release is a tag `vX.Y.Z` on a commit of `main` whose `ci` run passed (`DEVELOPMENT.md`, Releases), pushed by the maintainer only.
  - Issues are this repository's (`runsten-app/runsten`), the maintainer's as the contributors' ([`CONTRIBUTING.md`](CONTRIBUTING.md)). Never name one in a commit message, a comment or the README: the pull request carries the link, its description says `Closes #N`, and its merge closes the issue.
- **`docs/`** is a local, untracked folder of personal notes (design decisions, research). It may be missing.
  - If present, read it for context.
  - Never commit it, and never reference it from code, comments or the README.
